# Triage

Move issue notes under `.heio/` through a small state machine of triage roles.

Load **management**. That skill owns paths, templates, ids, status, and close-moves. Load **docs** for committed truth and for durable rejection notes. Load **planning-workflow** if the loop is unclear.

If `AGENTS.md` or `WORKSPACE.md` already names a tracker (`.scratch/`, `docs/planning/`, GitHub Issues), that file wins. Do not start a second tree.

Any triage notes or comment block you add to an issue must start with:

```
> *This was generated by AI during triage.*
```

## Creating a note

Copy the management issue template. **management** owns `<N>`. Scan live folders and `closed/`. Never pick the id by eye from the live folder alone.

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md). How to write durable agent briefs.
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md). How rejected-feature notes work under **docs**.

## Roles to frontmatter

Roles live in the issue note's frontmatter, not as GitHub labels.

- **State** rides on `status` plus a state tag. Issue `status` is `open | reviewing | promoted | closed | wontfix`.
- **Category** rides on `tags` and `labels` (`bug` or `feature` / `enhancement`).

Two category roles (apply exactly one):

- `bug`. Something is broken.
- `enhancement`. New feature or improvement.

Five state roles:

- `needs-triage`. `status: open` + tag `needs-triage`. Maintainer needs to evaluate.
- `needs-info`. `status: open` + tag `needs-info`. Waiting on reporter.
- `ready-for-agent`. `status: open` + tag `ready-for-agent`. Fully specified, AFK-ready. For single-unit work this is the executable. An agent working it flips `status: reviewing` (the claim), then `status: closed` when done.
- `ready-for-human`. `status: open` + tag `ready-for-human`. Needs human implementation.
- `wontfix`. `status: wontfix`. Will not be actioned.

Every triaged issue carries exactly one category tag and one state. If state roles conflict, flag it and ask the maintainer before doing anything else.

Edit the YAML directly. Swap the state tag in the same `tags` array.

State transitions: an untriaged issue (no state tag) normally goes to `needs-triage` first. From there it moves to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` once the reporter replies. An accepted, planned issue moves to `status: promoted` (a plan and tasks exist), then `status: closed` when done. The maintainer can override at any time. Flag transitions that look unusual and ask before proceeding.

### Terminal states are a flip and a move

Live folders hold only live issues. The moment an issue reaches `closed` or `wontfix`, set the status and `mv` it to `.heio/closed/`. Keep the filename. **management** owns the move. Setting `status` and stopping leaves the issue sitting in the active backlog.

After any close, live issue folders must not still hold terminal notes.

## Invocation

The maintainer invokes `/triage` and describes what they want. Interpret the request and act. Refer to issues by note slug or `issue-<N>`.

- "Show me anything that needs my attention"
- "Let's look at issue-42-foo"
- "Move issue-42-foo to ready-for-agent"
- "What's ready for agents to pick up?"

## Show what needs attention

Scan `.heio/inbox/issues/` and any matching notes in `closed/` you need for history. Read each note's frontmatter and present three buckets, oldest first (by `created_at`):

1. **Untriaged.** `status: open` with no state tag.
2. **`needs-triage`.** Evaluation in progress.
3. **`needs-info` with reporter activity in `## Comments` since the last triage notes.** Needs re-evaluation.

Show counts and a one-line summary per issue. Let the maintainer pick.

## Triage a specific issue

1. **Gather context.** Read the full issue note (body, `## Comments`, frontmatter `status`/`tags`, dates). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary discovered under `docs/`, respecting ADRs in the area. Run two checks against the codebase:
   - **redundancy.** Search for an existing implementation of the requested behaviour by domain concept, not the request's wording. Report where you looked. If found, it's an already-implemented `wontfix` (step 5).
   - **prior rejection.** Search `docs/` for rejection or out-of-scope notes (see [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)) and surface any that resembles this issue.

2. **Recommend.** Tell the maintainer your category and state recommendation with reasoning, plus a brief codebase summary relevant to the issue, including whether it's already implemented. Wait for direction.

3. **Verify the claim.** Before any grilling, check the claim actually holds. For a bug, reproduce it. Read the reporter's steps, trace the relevant code, run tests or commands. For any other claim, confirm it holds against the current code. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal). A confirmed repro makes a much stronger agent brief.

4. **Grill (if needed).** If the issue needs fleshing out, run a **grill-me** session.

5. **Apply the outcome.** Set the frontmatter `status`/`tags`, then write to the note:
   - `ready-for-agent`. Append an agent brief under `## Agent Brief` ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`. Same structure as an agent brief, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `needs-info`. Append triage notes (template below) under `## Comments`.
   - `wontfix` (already implemented). Append a `## Comments` note pointing at where the feature already lives (module or package, and the concept name it goes by), set `status: wontfix`, then move the note to `.heio/closed/`. Do not write a rejection note. That record is for rejected requests, and a built feature recorded there would poison the dedup check.
   - `wontfix` (bug). Append a polite explanation under `## Comments`, set `status: wontfix`, then move the note to `.heio/closed/`.
   - `wontfix` (enhancement). Write a durable rejection note through **docs**, `[[wikilink]]` it from a `## Comments` note, set `status: wontfix`, then move the note to `.heio/closed/` ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `closed` (fixed during triage, or the work landed). Append what was found and done under `## Comments`, set `status: closed`, then move the note to `.heio/closed/`.
   - `needs-triage`. Set the tag. Optional `## Comments` note if there's partial progress.

## Quick state override

If the maintainer says "move issue-42-foo to ready-for-agent", trust them and set the frontmatter directly. Confirm what you're about to do (status and tag changes, any note append), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief written into the note.

## Needs-info template

Append under the note's `## Comments` heading:

```markdown
> *This was generated by AI during triage.*

## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you:**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist in the note's `## Comments`, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
